# SPEC 02.3 — IAM Policy Scalability and Quota Guardrails

> **Status:** Implemented
> **Depends on:** SPEC 02.1, SPEC 02.2
> **Date:** 2026-10-16
> **Objective:** Add preventive local and read-only AWS validation that keeps every Gootip-managed IAM policy and role attachment below an intentional capacity budget before AWS quotas become deployment blockers.

## Why this spec exists

During SPEC 02.2, `GootipBootstrapAdminPermissions` reached 6,109 of the
6,144 non-whitespace character quota for an IAM customer managed policy. The
approved Core and State split restored capacity without broadening effective
permissions, but the repository had no preventive check before the AWS limit.

AWS currently limits each customer managed policy to 6,144 non-whitespace
characters. The current default quota for managed policies attached to a role
is 20 and can be increased to 25. Gootip will use lower repository budgets so
growth is reviewed before either AWS quota becomes urgent.

## Scope

**In:**

- A shared isolated evaluator for IAM customer managed policies declared in
  both `gootip-infra/` Terraform roots.
- Coverage of ordinary customer managed identity policies and customer managed
  permissions boundaries owned by Gootip.
- A 4,500-character warning threshold and a 5,500-character failure threshold
  per customer managed policy, measured after removing whitespace.
- An eight-attachment warning threshold and a ten-attachment failure threshold
  per Gootip-managed role.
- Attachment counts that include both AWS managed and customer managed policies
  attached to the role.
- Explicit exclusion of a permissions boundary from the role attachment count;
  its own policy document remains subject to the size budget.
- Fail-closed detection of declared policies that cannot be rendered, are not
  evaluated, or are duplicated under the same Terraform address or physical
  identity.
- Preservation of the SPEC 02.2 Core plus State semantic-equivalence check.
- Local tests for policy coverage, budget boundaries, attachment counts,
  duplicate statement SIDs, and isolated evaluator behavior.
- Read-only IAM Access Analyzer `ValidatePolicy` checks for every rendered
  Gootip customer managed identity policy.
- A temporarily applied Diagnostics expansion containing only the minimum
  regional Access Analyzer validation and Gootip IAM inventory reads, added by
  one separately reviewed apply and withdrawn by a second one, so the default
  configuration never keeps it.
- Read-only comparison of deployed Gootip-managed policy default versions and
  role attachments against the canonical Terraform configuration and state.
- Documentation for adding future capability-focused managed policies without
  expanding Core indefinitely.

**Out of scope (for future specs):**

- Splitting a current policy when it remains below the 5,500-character
  repository failure threshold.
- Creating placeholder policies for future network, database, runtime, or CI
  capabilities.
- Increasing an AWS IAM quota.
- Adding inline policies as overflow capacity.
- Replacing explicit least-privilege actions with wildcards to reduce policy
  length.
- Creating another human deployment role or changing the trust, session, MFA,
  source-user cutover, permissions-boundary, or state-ownership models from
  SPEC 02.1.
- Managing AWS-owned roles, policies, service-linked roles, Organizations,
  Identity Center, SCPs, RCPs, or roles under `/managed/`.
- Application infrastructure, RDS retry, Lambda/API deployment, networking,
  secret values, or any billable resource.
- GitHub Actions integration, which remains owned by SPEC 11.

## Policy-capacity model

### Size budgets

| Policy state | Non-whitespace characters | Required result |
| --- | ---: | --- |
| Healthy | 0–4,499 | Pass |
| Review | 4,500–5,499 | Pass with a visible warning |
| Repository limit reached | 5,500 or more | Fail before plan approval |
| AWS hard limit | More than 6,144 | Invalid independently of the repository check |

Whitespace and Terraform comments do not provide quota capacity because IAM
does not count whitespace against the managed-policy limit. The evaluator must
measure the rendered JSON document rather than source HCL length.

### Role attachment budgets

| Role state | Managed policy attachments | Required result |
| --- | ---: | --- |
| Healthy | 0–7 | Pass |
| Review | 8–9 | Pass with a visible warning |
| Repository limit reached | 10 or more | Fail and require a role-responsibility review |

The attachment calculation includes every Terraform-declared AWS managed or
customer managed policy attachment for the role. A permissions boundary is
reported separately and is not counted as an attached managed policy. Live
validation uses the same rule for roles already present in canonical state.

### Policy architecture

`GootipBootstrapAdmin` retains the capability-focused Core, State, and
Diagnostics policies established during SPEC 02.2. A future permission belongs
in Core only when it is intrinsic to bootstrap identity administration. State,
diagnostics, network, database, runtime, and CI capabilities remain separate
managed-policy domains.

A new capability does not automatically require a new policy. Related
statements may share a policy while it stays below the repository size budget.
Conversely, unrelated permissions must not be merged merely to conserve an
attachment slot. Reaching ten attachments requires reviewing the role's
responsibilities instead of bypassing the check.

Inline policies are not reserve capacity. Any future inline policy requires an
explicitly reviewed contract and aggregate entity-size controls; this spec does
not introduce one. Action or resource wildcards remain allowed only where the
AWS authorization model requires them and an existing test or new reviewed
assertion records that reason.

## Evaluation and validation model

### Required local evaluation

The local evaluator creates temporary policy-only copies of both Terraform
roots with an explicit local backend, empty local state, fake provider
credentials, disabled metadata lookup, and deterministic non-sensitive fixture
values for references that would otherwise be known only after apply. It must
not copy generated backend files, `.terraform/`, saved plans, state files, or
local audit evidence.

The evaluator runs with `-refresh=false` and must prove that every declared
`aws_iam_policy` is materialized from the current configuration. Conditional
policies and statements are evaluated in the configuration that produces their
maximum approved document. An unknown or missing policy document is a failure,
not permission to omit it from the report.

The shared implementation boundary is:

| File | Responsibility |
| --- | --- |
| `scripts/iam_policy_evaluator.py` | Build isolated roots, render policy documents, discover policy ownership, and derive role attachments |
| `scripts/check_iam_policy_guardrails.py` | Enforce size, coverage, SID, attachment, and wildcard-review invariants and print a deterministic summary |
| `scripts/validate_policies.py` | Render every configuration locally, call `ValidatePolicy` only, follow every finding page, and fail on blocking findings |
| `scripts/compare_iam_inventory.py` | Require refresh-free plans of both effective configurations to have no IAM changes, then compare canonical policy versions and role attachments with live IAM, without applying resources |
| `bootstrap/scripts/compare_bootstrap_policy_split.py` | Reuse the shared evaluator and compare the captured original Core baseline against current Core plus State |
| `scripts/tests/test_iam_policy_guardrails.py` | Exercise exact threshold boundaries, unknown documents, duplicate coverage, attachment counting, and normalization |
| `scripts/tests/test_validate_policies.py` and `scripts/tests/test_iam_inventory.py` | Exercise validation ordering, pagination, errors, findings, canonical inventory, semantic comparison, and drift |

Temporary files are removed on success and failure. Reports contain Terraform
addresses, policy names, counts, and finding codes only. Account IDs, complete
ARNs, plans, state, and policy documents remain untracked local evidence.

### Explicit read-only AWS validation

Remote validation is a separate operator action after all local checks pass and
SPEC 02.2 is complete. It uses a fresh MFA-backed
`GootipBootstrapAdmin` session and performs no IAM mutation.

For each rendered customer managed identity policy, the validator calls IAM
Access Analyzer `ValidatePolicy` with `IDENTITY_POLICY`. `ERROR` and
`SECURITY_WARNING` findings fail validation. `GENERAL_WARNING` and `SUGGESTION`
findings are reported with their finding code and reviewed disposition but do
not fail automatically.

The validator reads only `ValidatePolicy` and never calls `ListAnalyzers`, so
validation needs no analyzer configured in the account and no extra
authorization. `ValidatePolicy` paginates its findings, so the validator follows
every `nextToken` to exhaustion instead of trusting the first page: a document
declared clean from a partial read would be a false pass.

The live inventory resolves only policies and roles that Terraform owns and
that are present in canonical state. It reads each policy's default version and
each role's attached managed policies, normalizes order-insensitive JSON fields,
and compares them with the canonical rendered configuration. Missing,
additional, stale, or semantically different policy versions or attachments
fail validation. Expected future conditional resources that are absent from
canonical state are not reported as drift.

The Diagnostics expansion may grant only:

- `access-analyzer:ValidatePolicy` in `us-east-2` using the unavoidable
  wildcard resource required by the API.
- The IAM read operations required to fetch default versions and list
  attachments for Terraform-owned Gootip policy and role identities.
- The exact source-user read only if needed to verify a Terraform-owned
  permissions boundary; temporary external source-user administration remains
  governed by SPEC 02.1 and is not normalized as a role attachment.

No list-all-account authorization, policy creation, policy-version mutation,
attachment mutation, trust mutation, PassRole, secret access, or infrastructure
operation is authorized.

#### Temporary grant: D1, validate, D2

`diagnostics_inventory_enabled` defaults to `false`, and that default is the
configuration the account must return to. The grant is therefore never a
standing permission: it exists for exactly one validation window, and the flag's
default is its documented withdrawal target, so no later default plan
discovers an unexplained removal.

| Step | Configuration | Effect on `GootipBootstrapDiagnosticsPermissions` |
| --- | --- | --- |
| D1 apply | `diagnostics_inventory_enabled = true` | Adds exactly `ValidateGootipPoliciesInConfiguredRegion`, `ReadGootipManagedPolicyVersions`, and `ReadGootipRoleAttachments` (1 to 4 statements; the local render moves from 221 to 1,916 characters) |
| validation | unchanged | `scripts/validate_policies.py` from a fresh MFA-backed `GootipBootstrapAdmin` session |
| D2 apply | `diagnostics_inventory_enabled = false` (the default) | Removes exactly those three statements, returning the policy to its one-statement form |

Rules that make the sequence reversible rather than drifting:

- D1 and D2 are separate saved plans, each with its own review and its own
  explicit apply approval. Neither is applied without it, and neither plan is
  regenerated between review and apply.
- D1 must touch nothing but the Diagnostics policy: no other statement, no
  attachment, no role, no trust, no state, and no application resource.
- D2 must withdraw exactly those three statements and nothing else.
- After D2, both the normal plan and the `-refresh=false` plan must report no
  changes; that pair is the evidence the grant left no residue.
- Repeating a validation repeats D1 and D2. The grant is never left applied
  between validation windows, so the standing configuration keeps no
  `access-analyzer` authorization at all.

## Implementation plan

1. Revalidate the current official IAM managed-policy size and role-attachment
   quotas. Inventory every customer managed policy, permissions boundary, role,
   managed-policy attachment, conditional configuration, and existing wildcard
   justification in both Terraform roots.
2. Extract the isolated rendering logic from
   `bootstrap/scripts/compare_bootstrap_policy_split.py` into
   `scripts/iam_policy_evaluator.py`. Preserve the original baseline input and
   prove the existing Core plus State comparison still passes without a remote
   backend, canonical state, or AWS credentials.
3. Implement `scripts/check_iam_policy_guardrails.py` with complete policy
   discovery, maximum conditional evaluation, non-whitespace size measurement,
   global SID collision detection, wildcard-review coverage, and role
   attachment counting. Fail closed on unknown or omitted documents.
4. Add standard-library unit fixtures at every inclusive threshold and for
   AWS-managed attachments, customer-managed attachments, boundaries,
   duplicates, unknown values, and temporary-directory cleanup. Run the checker
   against both real Terraform roots.
5. Add the minimum Access Analyzer and Gootip inventory reads to
   `GootipBootstrapDiagnosticsPermissions`. Update Terraform assertions and
   prove that Core, State, deployment, runtime boundary, and source-user
   policies are otherwise unchanged.
6. Run formatting, validation, Terraform tests, Python tests, the exact Core
   plus State comparator, and the local guardrail checker. Resolve every failure
   without adding inline policies, broadening wildcards, or relaxing budgets.
7. Add `scripts/validate_policies.py` with the validator contract: it renders
   every configuration locally before any request, never calls
   `ListAnalyzers`, follows every finding `nextToken` to exhaustion, fails on
   `ERROR` or `SECURITY_WARNING`, and prints lower-severity findings with their
   code for review.
8. Produce and review the D1 saved plan with `diagnostics_inventory_enabled`
   set to `true`. Reject any change outside the three Diagnostics statements:
   no other statement, attachment, role, trust, state, or application resource.
9. After explicit apply approval, apply D1, mint a fresh MFA-backed
   `GootipBootstrapAdmin` session, and run the validator. Stop on any `ERROR`
   or `SECURITY_WARNING`.
10. Produce and review the D2 saved plan with the default `false`, apply it
    only after its own separate approval, and prove it withdraws exactly the
    three statements D1 added.
11. Run `scripts/compare_iam_inventory.py` with the effective variable files for
    both roots. Require refresh-free plans to show no pending IAM changes, then
    compare deployed default policy versions and role attachments read-only
    against canonical Terraform state. Finish with bootstrap refresh-free and normal no-change plans,
    both reporting no changes, and sanitized local evidence.
12. Document the policy-domain decision rule, thresholds, command order,
    warning interpretation, remote prerequisites, the D1/D2 repeat, and the
    procedure required when a size or attachment budget is reached.

## Decisions

- **Yes:** apply preventive controls to all Gootip customer managed IAM policies in both Terraform roots, including permissions boundaries.
- **Yes:** warn at 4,500 characters and fail at 5,500, leaving 644 characters before the AWS hard limit even at the repository failure boundary.
- **Yes:** warn at eight role attachments and fail at ten, reserving substantial capacity below the current AWS default quota.
- **Yes:** share one isolated Terraform evaluator between semantic-equivalence and capacity checks to avoid stale canonical-state values.
- **Yes:** validate remotely with IAM Access Analyzer and compare deployed default versions and role attachments read-only.
- **Yes:** fail Access Analyzer `ERROR` and `SECURITY_WARNING` findings while reporting lower-severity findings for review.
- **Yes:** place the minimum remote-validation authorization in Diagnostics rather than Core.
- **Yes:** grant it only temporarily, through a separately approved D1 apply and an equally separate D2 withdrawal, so the default configuration never keeps it and the flag's default `false` is the documented withdrawal target instead of silent drift.
- **No:** persist the Diagnostics grant as a standing permission; `access-analyzer:ValidatePolicy` and the inventory reads are needed only inside a validation window.
- **No:** treat whitespace removal as capacity engineering; IAM already excludes whitespace from its calculation.
- **No:** use inline policies as overflow or wildcard actions as compression.
- **No:** split healthy policies preemptively or create empty capability policies.
- **No:** make GitHub Actions or AWS credentials prerequisites for mandatory local checks.

## Risks

| Risk | Mitigation |
| --- | --- |
| A conditional policy is omitted from the evaluator | Evaluate maximum approved configurations and fail when declared addresses lack rendered documents. |
| Temporary evaluation accidentally reads canonical state or AWS | Use a clean directory, explicit local backend, fake credentials, disabled metadata access, empty state, and `-refresh=false`. |
| JSON ordering creates false drift | Normalize order-insensitive policy fields while preserving every IAM semantic field. |
| A warning becomes permanent technical debt | Print policy size, remaining repository capacity, owner, and required capability review on every warning. |
| Attachment counting misses AWS managed policies | Derive counts from every role-policy attachment regardless of policy owner and verify live attachments separately. |
| Remote validation permission becomes a control-plane expansion path | Keep it in Diagnostics, regional, read-only, tested against mutation actions, applied through one separately reviewed plan, and withdrawn through a second one after every validation, with two no-change plans as the residue check. |
| The grant survives its validation window | Require D1 and D2 as an explicit pair, forbid leaving the flag `true`, and treat a non-empty default plan after D2 as a failure. |
| Access Analyzer findings change as AWS evolves | Record finding codes and severity, re-run before IAM applies, and never suppress `ERROR` or `SECURITY_WARNING`. |
| A future role accumulates unrelated capabilities below numeric limits | Require domain ownership review independently of size and attachment counts. |

## What is **not** in this spec

- Application, database, network, Lambda, API Gateway, secret-value, or billing-resource deployment.
- A proactive split of policies that pass the 5,500-character repository budget.
- Inline-policy overflow, wildcard compression, IAM quota increases, or another human role.
- CI workflow implementation, source-user cutover, AWS-owned account-control management, or any non-validation AWS mutation.
