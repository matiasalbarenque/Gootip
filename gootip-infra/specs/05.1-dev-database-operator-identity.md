# SPEC 05.1 — Dev Database Operator Identity

> **Status:** Implemented
> **Depends on:** SPEC 02.1, SPEC 02.2, SPEC 03, SPEC 04, SPEC 05
> **Date:** 2026-10-19
> **Objective:** Create a dedicated MFA-backed human identity with controlled read/write access to application data in the dev PostgreSQL database without reusing application, migration, or master credentials.

## Why this spec exists

SPEC 03 created the restricted application and migration roles, while SPEC 05 removed the RDS master credential from the application runtime. Neither identity is appropriate for interactive human work: sharing `auth_runtime` would mix application and operator activity, and using `auth_migrator` or the RDS master would grant unnecessary administrative capability.

This spec establishes the human IAM, secret, and PostgreSQL identity boundary. It does not add a network route from a developer computer to the private database; SPEC 05.2 owns that connectivity and the DBeaver workflow.

## Scope

**In:**

- An MFA-protected `GootipDatabaseOperator` IAM role for the existing source user.
- A local `gootip-db-operator` AWS profile using the existing `gootip-mfa` source session.
- A bootstrap-owned `gootip-dev-db-operator` Secrets Manager container whose value is loaded outside Terraform.
- Exact secret-read permission for the database operator and the temporary administrative bootstrap function.
- A dedicated PostgreSQL login role named `gootip_dev_operator`.
- Read/write data access across explicitly declared application schemas, initially `auth`.
- Read-only access to `auth.gootip_schema_migrations`.
- Default privileges for future application objects created by approved owner roles.
- Local permission, isolation, idempotency, and future-object tests.
- The reviewed temporary deployment, invocation, and revocation procedure for `lambda_db_config`.

**Out of scope:**

- EC2, EC2 Instance Connect Endpoint, SSH forwarding, DBeaver configuration, or any workstation-to-VPC path; SPEC 05.2 owns those.
- Public RDS access, public subnets, Internet Gateway, NAT Gateway, Client VPN, or Systems Manager connectivity.
- PostgreSQL DDL, schema ownership, role administration, migration execution, or master-level access for the human operator.
- Reusing `auth_runtime`, `auth_migrator`, or the RDS master login for interactive work.
- Staging or production identities and database access.
- Automatic credential rotation or RDS IAM database authentication.

## Data model and integration contracts

### IAM identity

The bootstrap root owns one additional human role:

| Field                | Contract                                                                         |
| -------------------- | -------------------------------------------------------------------------------- |
| Role name            | `GootipDatabaseOperator`                                                         |
| IAM path             | `/gootip/operations/`                                                            |
| Trust                | Existing source user with MFA present and MFA age no greater than 10,800 seconds |
| Maximum role session | 3,600 seconds                                                                    |
| Local profile        | `gootip-db-operator` using `gootip-mfa` as `source_profile`                      |

The source user's assume-only policy and permissions boundary add only the exact database-operator role ARN. The operator role cannot assume another role, mutate IAM, read Terraform state, invoke Lambda, or administer Secrets Manager.

Before SPEC 05.2, its standing AWS permission is limited to `secretsmanager:DescribeSecret` and `secretsmanager:GetSecretValue` for the exact operator-secret ARN. Network-session permissions are added only by SPEC 05.2.

### Secret contract

The bootstrap root owns the empty `${project}-${env}-db-operator` container. For dev its physical name is `gootip-dev-db-operator`.

The out-of-band value has this exact shape:

```json
{
  "username": "gootip_dev_operator",
  "password": "loaded-out-of-band"
}
```

Terraform stores only the non-sensitive ARN. The value is generated or entered through the reviewed operator procedure, is never written to Git or a temporary plaintext file, and is never printed to normal command output. The loader rejects malformed JSON, a missing value, or a username different from `gootip_dev_operator` before opening a database connection.

The secret-container workflow extends the existing two-phase role-secret pattern:

1. A temporary name-and-required-tags permission creates only `gootip-dev-db-operator`.
2. The exact resulting ARN is reviewed and supplied to both Terraform roots as a non-sensitive reference.
3. The temporary create permission is removed before value access is granted.
4. `GootipBootstrapAdmin` may load or replace the exact value; `GootipDatabaseOperator` may only read it.

### PostgreSQL authorization contract

`gootip_dev_operator` is a `LOGIN` role with `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOREPLICATION`, and `NOBYPASSRLS`. It is not a member of `auth_runtime`, `auth_migrator`, the RDS administrative role, or any owner role.

Application schemas are an explicit code-owned allowlist. The initial value is:

```python
APPLICATION_SCHEMAS = ("auth",)
```

For every declared application schema, reconciliation grants:

- `CONNECT` on database `gootip`.
- `USAGE` on the schema.
- `SELECT`, `INSERT`, `UPDATE`, and `DELETE` on existing tables.
- `USAGE` and `SELECT` on existing sequences.
- Matching default privileges for future tables and sequences created by the approved schema owner.

After broad application grants, reconciliation explicitly reduces `auth.gootip_schema_migrations` to `SELECT` only. `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES`, and `TRIGGER` remain absent. System schemas, extension-owned schemas, and undeclared schemas are not added automatically. A future application schema requires a reviewed allowlist change and a new reconciliation.

### Files and ownership boundaries

| Boundary                         | Changes                                                                                                                               |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `gootip-infra/bootstrap/`        | Human role, source-user assumption allowlist, exact operator-secret container and permissions, variables, outputs, and phased runbook |
| `gootip-infra/` application root | Exact operator-secret ARN handoff and temporary `lambda_db_config` environment/IAM access only                                        |
| `gootip-db-config/`              | Fixed operator identity, credential loading, reconciliation, inventory helpers, and tests                                             |
| Project documentation            | Local profile setup, safe value loading, invocation, revocation, recovery, and rotation procedure                                     |

No secret value or secret version resource is introduced in Terraform.

## Implementation plan

1. Add failing unit and integration tests for the `gootip_dev_operator` credential contract, restricted attributes, application DML, migration-history read-only behavior, undeclared-schema denial, future objects, and repeated reconciliation.
2. Extend the bootstrap human-role trust and source-user assume-only allowlists with the exact `GootipDatabaseOperator` ARN. Add a least-privilege managed policy that initially reads only the exact operator secret.
3. Extend the existing phased secret-container workflow to create `gootip-dev-db-operator`, output its ARN, record the reviewed ARN references, remove the temporary creation grant, and enable exact manual value loading through `GootipBootstrapAdmin`.
4. Add the operator-secret ARN to the temporary `lambda_db_config` configuration and exact secret-read policy without broadening access to unrelated secrets.
5. Extend `gootip-db-config` to validate the fixed username, reconcile the role attributes and memberships, apply the declared-schema DML/default privileges, and restore the migration-history table to read-only after broad grants.
6. Complete local unit and disposable-PostgreSQL integration verification, including negative DDL, role, undeclared-schema, and history-mutation probes.
7. Apply the reviewed bootstrap capability and secret phases, load a non-production password without exposing it, re-enable the existing administrative Lambda through an exact saved application plan, and invoke the fixed `bootstrap` operation.
8. Inspect the sanitized reconciliation result, repeat the invocation to prove idempotency, then remove the administrative function/security group and withdraw temporary invocation permission according to the SPEC 03 revocation procedure.
9. Document `gootip-db-operator` profile configuration, credential replacement, failed-bootstrap recovery, and the explicit handoff to SPEC 05.2 for live workstation access.

## Acceptance criteria

- [ ] `GootipDatabaseOperator` uses the existing MFA-protected source-user trust contract and a one-hour role session.
- [ ] The source user can assume the exact database-operator role and gains no additional direct AWS capability.
- [ ] The operator IAM policy reads only `gootip-dev-db-operator` and cannot write secrets, read Terraform state, invoke Lambda, mutate IAM, or access application/master/migrator secrets.
- [ ] Terraform creates only the secret container and never stores, reads, plans, logs, or outputs its value.
- [ ] The out-of-band loader rejects any username other than `gootip_dev_operator`.
- [ ] `gootip_dev_operator` has none of `SUPERUSER`, `CREATEDB`, `CREATEROLE`, `REPLICATION`, or `BYPASSRLS` and has no privileged role membership.
- [ ] The operator can connect to `gootip` and select, insert, update, and delete ordinary tables in every declared application schema.
- [ ] The operator can use current and future sequences required by inserts.
- [ ] The operator can select from `auth.gootip_schema_migrations` but cannot insert, update, delete, truncate, trigger, or change it.
- [ ] The operator cannot create or alter schemas, tables, roles, ownership, extensions, or undeclared application objects.
- [ ] Repeated reconciliation is idempotent and does not remove or alter application data.
- [ ] Unit and disposable-PostgreSQL integration tests cover all positive and negative authorization cases.
- [ ] Bootstrap and application Terraform formatting, validation, and focused IAM/secret guardrail tests pass.
- [ ] The reviewed dev apply contains no unexpected delete, replacement, public networking, wildcard administration, or secret value.
- [ ] The temporary administrative Lambda and invocation permission are removed after successful reconciliation.
- [ ] Live access from a workstation is explicitly deferred to SPEC 05.2 and no temporary public database path is introduced for validation.

## Decisions

- **Yes:** use a dedicated IAM role, secret, and PostgreSQL login for interactive human activity.
- **Yes:** allow data reads and writes across explicitly declared application schemas.
- **Yes:** keep migration history readable for diagnosis but immutable to the human operator.
- **Yes:** reuse the idempotent SPEC 03 administrative Lambda and remove it again after reconciliation.
- **No:** reuse `auth_runtime`; human activity must not share application attribution or credential rotation.
- **No:** use `auth_migrator` or the RDS master; interactive work does not require DDL or administration.
- **No:** discover and grant arbitrary non-system schemas automatically; application scope remains reviewed and explicit.
- **No:** implement workstation networking in this spec; SPEC 05.2 owns that independent boundary.

## Risks

| Risk                                                             | Mitigation                                                                                                        |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Broad table grants accidentally include migration history writes | Apply the history-table revoke after every broad grant and assert the effective privileges in integration tests.  |
| A future schema is unexpectedly inaccessible                     | Require an explicit allowlist change and reconciliation instead of granting unknown schemas automatically.        |
| Operator and application credentials become coupled              | Keep separate roles, secrets, IAM permissions, and rotation procedures.                                           |
| A temporary administrative capability remains enabled            | Make revocation an acceptance item and verify the final normal Terraform plan.                                    |
| A password reaches logs or local files                           | Keep values outside Terraform, use hidden/generated input, sanitize errors, and never echo the value in runbooks. |

## What is **not** in this spec

- EC2 Instance Connect Endpoint, EC2 tunnel host, security-group connectivity, or a DBeaver profile.
- Public RDS access, NAT, VPN, SSM, RDS Proxy, or IAM database authentication.
- DDL, migration execution, database ownership, or role administration by a human operator.
- Staging, production, automatic rotation, or a permanent administrative runtime.
