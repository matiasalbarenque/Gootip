# SPEC 03.1 — IAM Managed-Policy Capacity Split

> **Status:** Implemented
> **Depends on:** SPEC 02.1, SPEC 02.2, SPEC 02.3, SPEC 03
> **Date:** 2026-10-16
> **Objective:** Split the Gootip managed policies that exceed or approach the 6,144-character IAM limit into capability-scoped policies that each stay below 4,500 non-whitespace characters, without changing any effective permission.

## Why this spec exists

SPEC 02.3 added a preventive capacity checker but deliberately deferred the actual split of policies that still exceed the repository budget. SPEC 03 measured `GootipTerraformDeployPermissions` at 6,046 of the 6,144 non-whitespace characters (98 characters of headroom) and a bootstrap apply already failed with `LimitExceeded: Cannot exceed quota for PolicySize: 6144`.

`GootipBootstrapAdminPermissions` sits at 5,258 characters (warning state) and grows again when SPEC 03 loads the two role-secret containers. Creating the new split policies also requires the bootstrap admin to create and attach them, so the admin policy must gain capacity before the deploy policy can be split.

This spec performs the split only. It adds no capability, removes none, and does not execute the SPEC 03 role-secret transition.

## Scope

**In:**

- Split `GootipTerraformDeployPermissions` into capability-scoped customer managed policies.
- Split `GootipBootstrapAdminPermissions` first, to create headroom for the new policy-management ARNs.
- Preserve the effective permission set per role exactly: same actions, resources, conditions, effects, and denies.
- Keep every role below the eight-attachment warning budget of SPEC 02.3.
- Update Terraform assertions, the Core/State split comparator, the wildcard review map, and README documentation.
- Produce a reviewed bootstrap-only plan and apply it through a fresh MFA-backed bootstrap session.

**Out of scope (for future specs):**

- Executing the SPEC 03 role-secret container transition or loading any secret value.
- Adding, removing, or broadening any permission, wildcard, or condition.
- Increasing any AWS IAM quota.
- Inline policies as overflow capacity.
- Splitting policies that already render below 4,500 characters.
- Application, RDS, network, Lambda, or API Gateway resources.

### Transition — three applies (A/B/C)

The bootstrap admin role holds no permanent customer-managed-policy creation
grant beyond the SPEC 03 PassRole exception, so the standing configuration
cannot create the four new policies. SPEC 02.3 already recorded that a new
managed policy needs a separately reviewed temporary creation grant. This spec
makes that grant explicit through one flag, `split_policy_creation_enabled`
(`bootstrap/variables.tf`, default `false`), mirroring the existing
`role_secret_creation_enabled` idiom.

While the flag is true the Core policy document merges one extra statement,
`CreateExactSplitPolicies`, scoped to exactly the four new policy ARNs
(`iam:CreatePolicy` plus tag bookkeeping; no delete). A policy cannot create
itself, so the grant lives in the retained Core rather than in the policy-admin
capability it creates. The standing (default) configuration renders no
`CreateExactSplitPolicies`, so the split introduces no permanent
policy-creation authorization; the pre-existing SPEC 03
`CreateExactAdministrativePassRolePolicy` exception is unchanged and out of
scope here.

| Apply                     | Flag  | Scope                                                                    | Permitted mutations                                    |
| ------------------------- | ----- | ------------------------------------------------------------------------ | ------------------------------------------------------ |
| **A — grant**             | true  | `-target=aws_iam_policy.bootstrap_permissions`                           | new version of `GootipBootstrapAdminPermissions` only  |
| **B — create and attach** | true  | the four new policies and their attachments                              | the four new policies and their role attachments       |
| **C — withdraw**          | false | a full default plan, no `-target`                                                     | `GootipBootstrapAdminPermissions` version only         |

While the flag is true the retained core also merges one lifecycle statement,
`ManageExactHumanRolesAndPolicies`, which the policy-admin capability will own.
Apply A never drops `iam:AttachRolePolicy` or `iam:CreatePolicyVersion` before
that capability exists, so apply B can create the four policies, attach them to
their roles, and update `GootipTerraformDeployPermissions`. Apply C withdraws both
the grant and the retained statement from the core.

Only that one statement is retained. Retaining all three lifecycle statements
together with the grant rendered the pre-split core at 6,192 non-whitespace
characters, past the 6,144 AWS quota, and the first attempt to apply A failed
with `LimitExceeded: Cannot exceed quota for PolicySize: 6144`. The other two
statements (`ManageExactSplitPolicyTags` and
`CreateExactAdministrativePassRolePolicy`) are therefore withdrawn by apply A.
Apply B does not need them: the `CreateExactSplitPolicies` grant covers policy
tagging on the four new ARNs, and the SPEC 03 PassRole policy already exists.

The retained statement reads from one shared document
(`bootstrap_role_policy_lifecycle`), which the policy-admin capability also
sources, so the overlap is a single definition and IAM unions make it harmless.

#### The transition is the only render allowed into the warning band

The standing configuration keeps every policy below the 4,500-character healthy
budget. The short-lived transition is the one exception: apply A sends the
retained core with the temporary grant, the largest document this repository
produces, so it may sit in the 4,500–5,499 warning band. It must still stay below
both hard ceilings:

| Limit                                    | Value | Applies to                                                    |
| ---------------------------------------- | ----: | ------------------------------------------------------------- |
| AWS `PolicySize` quota                   | 6,144 | every rendered policy, including the transition               |
| Repository transition failure limit      | 5,500 | `aws_iam_policy.bootstrap_permissions` while the flag is true |
| Repository healthy warning budget        | 4,500 | every standing (default-flag) configuration                   |

`iam_policy_evaluator.BOOTSTRAP_TRANSITION` renders exactly that configuration
(the pre-split live shape with `split_policy_creation_enabled = true`), and
`check_iam_policy_guardrails.Report.check_transition_core` fails the build if the
rendered size reaches 5,500, if it exceeds 6,144, or if the core does not carry
exactly `CreateExactSplitPolicies` and `ManageExactHumanRolesAndPolicies`. The
checker's fixture render currently measures 5,256 characters and 12 statements;
the equivalent document against the live account, the largest value this
repository sends to AWS, measures 5,269.

The other maximum render is the SPEC 03 role-secret ARN handoff
(`BOOTSTRAP_ROLE_SECRET_MAXIMUM`), where both exact role-secret ARNs replace the
reviewed name patterns and grow the core and the application runtime boundary. It
stays healthy — the largest policy is 3,409 characters — and
`check_role_secret_maximum` gates it against the same two ceilings, so the handoff
cannot reintroduce the quota failure this split removed. Both gates run locally
and neither requires an AWS apply; the `access-analyzer` validation below is
separate.

Each apply is a reviewed saved plan and a separate approval. The order is
mandatory: the admin grant (A) must land before the deploy split can create
anything (B), and the flag must return to `false` (C) so the final configuration
retains no policy-creation authorization. Apply A is targeted at
`aws_iam_policy.bootstrap_permissions` so granting one statement never requires
touching unrelated resources. Apply C is deliberately a full default plan with
no `-target`: after A and B the default configuration differs from AWS only by
the four temporary SIDs, so a correct C shows exactly one resource change.

#### The SPEC 02.3 diagnostics authorization is out of scope here

`GootipBootstrapDiagnosticsPermissions` is the target of three read-only SPEC
02.3 statements (Access Analyzer `ValidatePolicy` plus a managed-policy and a
role-attachment inventory). That authorization belongs to SPEC 02.3 and has
nothing to do with the capacity split, so it is gated behind its own fail-closed
variable, `diagnostics_inventory_enabled` (default `false`), and SPEC 03.1 never
sets it. Consequently every plan above renders the diagnostics policy exactly as
it already exists in AWS — one `LookupFoundationCloudTrailEventsInRegion`
statement — and **plan B carries no diagnostics delta**. Verified by rendering
the configuration with the split flag off and on: only
`GootipBootstrapAdminPermissions` differs, and the diagnostics document is
byte-identical in both.

The guardrail checker still reviews that authorization, but from its own
`bootstrap-diagnostics` render, so the wildcard review of the SPEC 02.3
statements is preserved without folding them into SPEC 03.1's bootstrap renders.
`run "bootstrap_diagnostics_inventory_is_deferred"` asserts that with the flag
off the policy contains exactly the applied statement and no `ValidatePolicy`
action.

Once SPEC 03.1 has fully converged, the three statements are presented as a
**separate SPEC 02.3 plan and approval**: setting
`diagnostics_inventory_enabled = true` for one reviewed apply adds only those
three read-only statements and nothing else.

#### Saved plans are regenerated, not carried forward

A saved plan is a snapshot of one specific state. A plan rendered before apply A
cannot describe a state that apply A has already changed, so **only plan A is
presented for approval; B and C are rendered after the preceding apply and a
pre-A rendering of either is never executable evidence.**

| Plan | Rendered against | Command | Permitted mutation |
| --- | --- | --- | --- |
| **A** | current (pre-A) state | `terraform plan -out=A -var=split_policy_creation_enabled=true -target=aws_iam_policy.bootstrap_permissions` | `aws_iam_policy.bootstrap_permissions` only: add `CreateExactSplitPolicies`, retain `ManageExactHumanRolesAndPolicies`, withdraw `ManageExactSplitPolicyTags` and `CreateExactAdministrativePassRolePolicy` |
| **B** | state after A | `terraform plan -out=B -var=split_policy_creation_enabled=true` | the four new policies, their four attachments, and `GootipTerraformDeployPermissions` (the statements moved out of it) — nothing else |
| **C** | state after B **and** `GootipBootstrapPolicyAdminPermissions` verified effective on `GootipBootstrapAdmin` | `terraform plan -out=C` (default flag, **no `-target`**) | `aws_iam_policy.bootstrap_permissions` only, removing exactly `CreateExactSplitPolicies` and `ManageExactHumanRolesAndPolicies` |

Before C is rendered, confirm the capability is live:

```bash
aws iam list-attached-role-policies --role-name GootipBootstrapAdmin
# must include GootipBootstrapPolicyAdminPermissions
```

C is deliberately planned **without `-target`**: after A and B the default
configuration differs from AWS only by the two SIDs C removes, so a correct C
shows exactly one resource change, `aws_iam_policy.bootstrap_permissions`. Any
second resource change means something outside this spec drifted, and the apply
must stop. The full four-SID transition — two withdrawn by A, two by C — is
asserted by `run "bootstrap_split_policy_lifecycle_is_exact"`, the temporary
document's two-SID shape by
`run "bootstrap_split_creation_grant_is_temporary_and_exact"`, and the transition
size by `check_iam_policy_guardrails.Report.check_transition_core`.

After C, a default plan with **no `-var` and no `-target`** must report no
changes at all. That is the convergence signal for this spec, and it is also the
point at which the separate SPEC 02.3 diagnostics change below may be
introduced.

## Implementation plan

1. Reconcile the current bootstrap state after the partially applied SPEC 03 phase-1 apply and record a refresh-free plan baseline.
2. Split `GootipBootstrapAdminPermissions`: move the role-policy lifecycle statements into `GootipBootstrapPolicyAdminPermissions`, list the new split policy ARNs in the retained core, and keep the original Core+State comparator baseline valid. Run `terraform validate` and the local guardrail checker.
3. Verify the admin split renders every policy below 4,500 characters and the bootstrap role below 8 attachments.
4. Split `GootipTerraformDeployPermissions`: extract the network, database, and foundation-read documents and attach them to `GootipTerraformDeploy`.
5. Prove the deploy role's effective permissions are equal in effect to the pre-split policy by unioning the new documents and comparing normalized statements.
6. Update `bootstrap/tests/iam.tftest.hcl`, `bootstrap/tests/role_secrets.tftest.hcl`, the checker wildcard review map, the Core/State comparator baseline, and READMEs.
7. Produce and present plan **A** only. After A is applied, render a fresh B against the new state; after B is applied and `GootipBootstrapPolicyAdminPermissions` is verified effective on the admin role, render a fresh C against that state. Never reuse a saved plan across an apply. Reject any mutation, deletion, trust change, or state change outside the transition table above.
8. After explicit approval for each step, apply A then B then C through a fresh MFA-backed `GootipBootstrapAdmin` session, then run IAM Access Analyzer `ValidatePolicy` on every rendered policy.
9. Confirm the final default plan reports no changes, and verify locally — with no apply — that the two maximum renders stay inside both ceilings: the SPEC 03.1 transition core (`BOOTSTRAP_TRANSITION`) and the SPEC 03 role-secret ARN handoff (`BOOTSTRAP_ROLE_SECRET_MAXIMUM`).
10. Only after SPEC 03.1 has converged, present the three read-only SPEC 02.3 diagnostics statements as their own plan and approval by setting `diagnostics_inventory_enabled = true` for one apply. That change is never part of applies A, B, or C.

## Decisions

- **Yes:** split by capability domain (network, database, foundation reads, policy administration) rather than by action type or service.
- **Yes:** split the bootstrap admin policy first, because creating the new deploy policies requires the admin to create and attach their ARNs.
- **Yes:** retain the existing physical policy names for the core policies to avoid destroy-and-recreate churn.
- **Yes:** target below 4,500 characters per policy, the healthy budget of SPEC 02.3.
- **Yes:** realize the temporary policy-creation grant as a default-off `split_policy_creation_enabled` flag, withdrawn in apply C, so the standing configuration introduces no permanent policy-creation authorization.
- **Yes:** retain only `ManageExactHumanRolesAndPolicies` in the core during the transition, because retaining all three lifecycle statements together with the grant overflowed the 6,144-character AWS quota (6,192 rendered); the standing configuration still holds the full capability.
- **Yes:** allow the short-lived transition core into the 4,500–5,499 warning band while keeping every standing configuration below 4,500.
- **No:** raising the AWS IAM quota.
- **No:** inline policies as overflow or wildcard compression to shorten documents.
- **No:** changing any effective permission while splitting.
- **No:** executing the SPEC 03 role-secret transition in this spec.

## Risks

| Risk                                                                     | Mitigation                                                                                   |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| Creating the new policies needs an already-expanded admin policy         | Split the admin policy first and prove headroom before adding the new ARNs.                  |
| A partially applied SPEC 03 change leaves drift in bootstrap state       | Reconcile state and take a refresh-free baseline before any mutation.                        |
| The Core/State comparator baseline becomes invalid after a further split | Update the recorded baseline to the new Core plus extracted policies and re-assert equality. |
| The wildcard review map is keyed by physical policy name                 | Move each reviewed entry to the new policy name in the same change.                          |
| Attachment count grows toward the role quota                             | Keep each role below eight attachments and re-check after the split.                         |
| A permission is silently dropped or duplicated while moving statements   | Compare the union of normalized statements per role before and after.                        |
| The temporary creation grant is left enabled after the split             | Apply C with the default flag; the comparator fails if `CreateExactSplitPolicies` is present in the standing configuration. |
| The retained transition core plus the temporary grant exceeds the 6,144 quota | Retain only the single lifecycle statement apply B needs and gate the transition render against both the 5,500 and 6,144 limits. |

## What is **not** in this spec

- Secret-value loading, the role-secret transition, or any SPEC 03 completion.
- New capabilities, permissions, wildcards, or quota changes.
- Application, database, network, Lambda, or API Gateway resources.
- CI/CD workflow implementation.
