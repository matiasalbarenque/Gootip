# SPEC 02.1 — IAM Roles, STS MFA, and Terraform Bootstrap

> **Status:** Implemented
> **Depends on:** SPEC 02 (historical access-model reference)
> **Date:** 2026-10-14
> **Objective:** Run Gootip Terraform through MFA-protected STS roles and an independent bootstrap control plane in the existing AWS Sign up for AWS (new) project, without activating Advanced Features or managing AWS-owned account controls.

## Purpose and scope

The active account is an AWS Sign up for AWS (new) Free Plan project assigned to `us-east-2`. AWS owns its Organization, IAM Identity Center, Account Access Manager, IAM Role Manager, project-access roles, SCPs, and RCPs. They are immutable external dependencies, not Gootip Terraform resources.

This spec owns:

- The `gootip` programmatic source user and MFA/STS flow.
- `GootipBootstrapAdmin`, `GootipTerraformDeploy`, and the application runtime boundary.
- The independent `gootip-infra/bootstrap/` Terraform root.
- The state bucket, keys, account guards, migration safety, and recovery contract.
- The empty application-secret container and value-blind Terraform contract.
- The deferred source-user cutover.

[SPEC 02.2](02.2-secure-dev-foundation-deployment.md) owns permissions and deployment for the private network, protected RDS instance, endpoint, and CA layer. [SPEC 10](10-final-dev-application-deployment.md) owns the final authentication Lambda and HTTP API deployment, while SPEC 11 owns future CI/OIDC roles. None may take ownership of this spec's bootstrap resources.

Out of scope: staging/production, cross-account access or tests, customer-managed Organizations/Identity Center, Advanced Features, secret values in Terraform, customer KMS keys, DynamoDB locks, Object Lock, replication, and code-publication separation.

## Contracts

### Account and preflight

AWS Settings is the independent source for project, Account ID, assigned Region, plan, credits, and expiration. The repository must not create another account, leave or modify the AWS-managed organization, replace its identity source, disable IAM Role Manager, activate Advanced Features, or convert the plan.

Verify four independent gates before mutation:

1. **Project:** Builder ID MFA selects the exact project and confirms its twelve-digit Account ID and `us-east-2` assignment.
2. **Identity:** `aws sts get-caller-identity --profile gootip-dev` resolves to the existing `gootip` user in that account.
3. **Eligibility:** AWS Settings shows `FREE` and `ACTIVE`; authorized Free Tier/IAM reads are supporting evidence only. Never add a grant to bypass a denied eligibility read.
4. **Compatibility:** Inventory every state candidate, owner, Region, key, lock, lineage, serial, encryption, and managed-resource Region without writing state.

Inaccessible or uncertain state, a foreign owner, unexplained lock, Region mismatch, managed `us-east-1` resource, unknown authorization denial, or denial of a required operation is a hard stop. Authentication alone does not prove eligibility, state safety, or authorization.

Terraform must not manage or import Organizations, Identity Center/Identity Store, Account Access Manager, IAM Role Manager, project-access or service-linked roles, SCPs, RCPs, or roles under `/managed/`.

### Identities and sessions

The project owner uses Builder ID and AWS Settings for project access, billing, value-only secret fallback, and recovery. Builder ID MFA is separate from the IAM TOTP required by STS.

`gootip` is programmatic only. Its long-term key remains solely in local profile `gootip-dev`; one-hour temporary credentials are minted into `gootip-mfa`:

```bash
aws configure mfa-login --profile gootip-dev \
  --duration-seconds 3600 --update-profile gootip-mfa
```

Role profiles use `gootip-mfa` and these exact paths:

```text
/gootip/bootstrap/GootipBootstrapAdmin
/gootip/deployment/GootipTerraformDeploy
```

Both roles trust only the exact source user for `sts:AssumeRole`, require present MFA no older than 3600 seconds, and limit sessions to 3600 seconds. Expired or stale MFA requires a new source session.

No credential, token, MFA seed, password, secret value, account-specific ARN/bucket, Account ID, or generated backend file may be committed. Account identifiers are generated local inputs, not repository constants.

### Permissions

`GootipBootstrapAdmin` is a scoped control-plane role, not account-wide `AdministratorAccess`. It manages only the exact Gootip identities/policies, source-user cutover resources, state controls and approved versions, and the exact application-secret exception.

`GootipTerraformDeploy` currently receives only:

- Exact application state read/write and lock read/write/delete, without state deletion or bootstrap access.
- Region-scoped `ec2:DescribeAvailabilityZones`.
- `rds:DescribeDBEngineVersions` and `rds:DescribeOrderableDBInstanceOptions` on `*` because they have no resource type.
- `rds:DescribeDBInstances` on only the generated `gootip-auth-dev` DB ARN.
- Read inspection of approved application IAM paths.
- `iam:PassRole` for enumerated application Lambda roles with `iam:PassedToService = lambda.amazonaws.com`.

It cannot administer the source user, operator roles, bootstrap policies/boundaries, bucket controls, AWS-managed account controls, unrelated roles, secret containers/policies, or secret values. It has no application-resource mutation permission until the owning dependent spec obtains a separately reviewed bootstrap policy change.

Runtime roles use `/gootip/application/` and the exact bootstrap-owned `GootipApplicationRuntimeBoundary`. The boundary excludes IAM administration, STS role assumption, `iam:PassRole`, state access, and unrelated secrets. Bootstrap owns every boundary and PassRole expansion.

### State

The bucket is exactly `gootip-terraform-state-<ACCOUNT_ID>`, derived from signed STS identity and independently confirmed in AWS Settings. A collision, foreign/uncertain owner, or Region other than `us-east-2` stops execution; there is no fallback name.

| Root        | State                          | Lock                                  |
| ----------- | ------------------------------ | ------------------------------------- |
| Bootstrap   | `bootstrap/terraform.tfstate`  | `bootstrap/terraform.tfstate.tflock`  |
| Application | `gootip/dev/terraform.tfstate` | `gootip/dev/terraform.tfstate.tflock` |

Both roots require Terraform 1.10+, `use_lockfile = true`, explicit backend/provider account allowlists, `us-east-2`, and the default workspace only.

The bucket uses bucket-owner enforcement, all public-access blocks, versioning, SSE-S3 `AES256`, TLS-only access, and `prevent_destroy`. It has no public ACL/policy, customer KMS key, replication, Object Lock, or automatic version deletion.

Bootstrap can read/write but not delete its state object, manage only its exact lock, and inspect/restore approved state versions. Deployment cannot access bootstrap state, bucket controls, or historical versions.

Bootstrap begins with local state. Migration requires protected backups, verified ownership, an empty destination, and `terraform init -migrate-state`; `-force-copy` is prohibited and `-reconfigure` cannot substitute for migration. Lineage/serial differences block progress unless comparison proves identical resources, instances, attributes, and outputs after excluding only `lineage`, `serial`, and equivalent `check_results` ordering. Refresh-free and normal no-change plans must pass before cleanup.

The renderer validates profile, assumed role, Account ID, Region, bucket owner, canonical key, allowlist, and stale output files before writing ignored backend configuration. It never moves state.

### Secrets

Bootstrap owns one empty `gootip-auth-dev` secret container. Terraform never manages, reads, accepts, or stores a secret value/version.

Bootstrap may refresh/tag that exact container and manually describe/get/put only its value; those value actions are denied for every other secret. Deployment cannot manage or read secrets.

The preferred value procedure uses fresh bootstrap credentials and avoids history, arguments, logs, files, Terraform, and Git. The AWS-managed project Console is a value-only fallback: verify project/Region, change only the exact value, and retain CloudTrail evidence. IAM and secret-policy changes remain Terraform-only.

SPEC 02.2 creates RDS with `manage_master_user_password = true` and returns only its non-sensitive secret ARN. A later bootstrap change validates that ARN, denies bootstrap access to it, and adds only the exact runtime read ceiling required by approved dependent specs. No handoff reads a value.

### Authorization and recovery

Effective access is the intersection of identity/resource policies, boundaries, sessions, SCPs, and RCPs. Positive tests must pass under that intersection. Every negative live denial also needs a Terraform assertion or same-account IAM simulation proving Gootip policy is restrictive without relying solely on an SCP.

Only `iam:GetLoginProfile` may be accepted as denied, and only when it matches the published Free Plan `DenyIAMRestrictedActions` statement. Validation or missing-resource errors are not authorization evidence.

Recovery uses a fresh AWS Settings project-owner session and `aws login` to run the tracked bootstrap root against the unchanged backend. No ad hoc Console IAM edit, `aws iam` mutation, reconstructed state, or manual overwrite is allowed. If the session cannot access state, an SCP blocks repair, or ownership is uncertain, stop and escalate to AWS Support.

## Staged operation

### Phase A — Bootstrap baseline

The implemented baseline establishes:

1. Read-only account, Region, state, and authorization compatibility checks.
2. Import and destroy protection for `gootip` while its temporary administrative grant remains available.
3. IAM-only creation of roles, policies, and boundaries with account resources disabled.
4. Fresh MFA role assumption and denial without MFA.
5. Gated bucket and empty-secret creation/adoption.
6. Protected bootstrap-state migration and no-change verification.
7. Application compatibility planning without applying resources. The recorded plan proposed 32 creates and required only baseline Availability Zone discovery.

Phase A does not authorize an application apply or source-user lockdown.

### Dependent deployment handoffs

SPEC 02.2 inventories every action required by the saved foundation plan. Each later deployment spec repeats that process for its own delta. Every request records action, scope, conditions, wildcard reason, tests, and rollback. Bootstrap applies each policy diff separately from its application apply.

SPEC 02.2 owns RDS-first deployment, the master-secret ARN handoff, and exact DB discovery. SPECS 03 through 09 own their focused private and security controls. SPEC 10 owns final Lambda PassRole tests, public application deployment, and functional validation, while SPEC 11 owns later CI/CD automation.

### Phase B — Source-user cutover (deferred)

Phase B remains disabled until SPEC 10 final deployment evidence and recovery prerequisites exist:

1. Prove both roles, state, authorization tests, and a fresh project-owner no-change recovery plan.
2. Attach the assume-only boundary while temporary grants remain; mint fresh MFA credentials from the permanent key and retest both roles.
3. Remove every administrative managed/inline policy, group membership, and direct resource-policy grant through reviewed Terraform.
4. Discard old sessions, mint MFA again, verify both role ARNs, and prove direct source-user resource access is denied.
5. Record final IAM inventory and exercise non-destructive Terraform-only recovery.

Any failure stops cutover. The final source identity may assume only the two exact roles and has no direct application, backend, IAM-administration, secret, or billing access.

## Known gaps

Earlier revisions claimed capabilities not present in the current repository:

- `bootstrap/.envrc` does not override the parent deployment profile with `gootip-bootstrap-admin`.
- The renderer supports only canonical `application` and `bootstrap` modes, not recovery mode.
- `bootstrap/README.md` lacks the complete cutover, live-authorization, and recovery runbooks.
- Phase B does not yet model removal of every possible pre-existing user/group/resource-policy grant; enabling its flag alone does not authorize cutover.
- Application mutations and infrastructure-dependent live tests remain intentionally staged behind SPECS 02.2 through 12.

These require separately reviewed implementation changes; compacting this spec does not approve or resolve them.

## Residual risks

- AWS-managed policies, eligibility, credits, and restrictions can change; revalidate rather than broadening IAM.
- State uncertainty, foreign ownership, Region mismatch, or unexplained migration divergence remains fail-closed.
- Cached credentials can hide a broken cutover path; proofs use newly issued MFA and role sessions.
- Lambda code publishers can indirectly use allowed runtime secrets. Exact boundaries limit but cannot remove this exposure.
- The project Console fallback is broader than bootstrap and is permitted only for value-only secret operation with CloudTrail evidence.
