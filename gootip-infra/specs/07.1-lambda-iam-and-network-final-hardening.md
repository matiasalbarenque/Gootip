# SPEC 07.1 — Lambda IAM and Network Final Hardening

> **Status:** Implemented
> **Depends on:** SPEC 02.1, SPEC 02.2, SPEC 03, SPEC 04, SPEC 05, SPEC 06, SPEC 07, SPEC 08, SPEC 09, SPEC 14; gootip-core SPEC 02 and SPEC 06
> **Date:** 2026-10-30
> **Objective:** Finalize least-privilege IAM, logging, invocation, endpoint, and private-network controls for every implemented application, migration, and administrative Lambda before final deployment automation.

## Deployment ownership amendment (2026-10-30)

SPEC 10's Draft scope includes both Auth and Core initial API deployment.
References below to a future Core deployment spec now bind to SPEC 10 for exact
runtime resources, concurrency, routes/JWT and initial live IAM/TLS/security
checks. SPEC 10.1, dependent on completed SPEC 10, owns traffic/connection-peak,
live refresh/rotation, controlled failures and recovery exercises for both APIs.
SPEC 11 cloud automation consumes both handoffs. This ownership update changes
no completed evidence, existing approval or activation authority. Historical
references assigning live rotation to SPEC 10 delegate that exercise to SPEC 10.1;
they do not make operational acceptance an initial-deployment completion gate.

## Why this spec exists

Auth and Core now have executable services and reviewed database contracts.
SPEC 09 supplies runtime credential refresh for both, including Auth signing-key
history. SPEC 14 and Core SPEC 06 supply Core's administrative and private
migration contracts. SPEC 07 remains the development IAM/network baseline.

The API deployments are still deferred. Terraform defines disabled Auth runtime
resources, but no Core API runtime resources. Hardening must therefore separate
existing infrastructure, prepared Auth configuration, and Core's future deployment
contract instead of requiring both public APIs before work can begin.

### Phases and completion boundary

| Phase                         | Work owned here                                                                                                | Evidence required here                                                                                     |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| A — Prepare                   | Exact inventory, bootstrap permissions, policies/rules for existing resources, and disabled Auth configuration | Offline policy/plan tests, dependency checks, transition/rollback plans                                    |
| B — Harden existing resources | Reviewed dev changes to administration, both migration executors, and shared network/endpoint controls         | Current policy inspection and scoped positive/negative verification for deployed resources                 |
| C — Validate API deployment   | Auth under SPEC 10; Core under its future deployment spec                                                      | Live secret stages, TLS, connectivity, logs, interface lifecycle, and authorization evidence at deployment |

Approval requires actual source contracts and exact identities for resources
already defined in Terraform, not deployment of the APIs. Completion of A and B
may mark this spec Implemented only with the Phase C checklist and owners
recorded explicitly. Phase C checks remain pending, never represented as passed.
Unresolved Phase B requirements remain blockers except for Admin runtime checks
covered by the approved residual-risk disposition above.

SPEC 10 consumes the prepared Auth configuration and Phase B evidence, then
performs its own Auth activation checks. A future Core deployment spec must
introduce exact Core API identities/resources and apply this contract before
activation. Neither depends on completion of the other's live API checks.

## Scope

**In:**

- Inventory of every implemented authentication, core, migration, and administrative Lambda and every AWS API call reachable from its code.
- Independent final execution-role policies for existing functions and disabled Auth resources, plus the binding requirements for future Core API policies.
- Exact bootstrap-owned policy-management and attachment permissions needed for the transition, with focused guardrail tests and ordered saved plans.
- Exact secret ARN allowlists derived from effective function configuration, including valid reviewed overrides.
- Log stream creation and log writes restricted to each function's Terraform-managed log group.
- Required Lambda VPC interface permissions with an AWS-recommended conditional denial for calls made by function code.
- Operator-only administrative invocation with a tested revoke/re-enable procedure.
- Removal of redundant broad managed-policy attachments after replacement policies are active.
- Client security-group egress restricted to exact PostgreSQL and Secrets Manager destinations required by each function.
- RDS ingress restricted to the exact implemented application, migration, administrative, and temporary operator client groups.
- A Secrets Manager endpoint policy restricted to exact function principals, read actions, and configured secret ARNs.
- IAM inspection, context-aware policy evaluation, and deployed positive/negative checks according to the phase boundary above.
- Accurate documentation of unavoidable wildcard resources and the reason for each exception.
- Confirmation that private DNS, native Lambda logging, secret retrieval, and PostgreSQL access work without NAT or a Logs VPC endpoint.

**Out of scope:**

- Implementing `gootip-core`, its business rules, schema, database role, secret containers, migrations, or migration executor.
- Creating or deploying Core API runtime resources, or activating Auth. Their deployment specs own creation/activation and public routing.
- Changing application behavior to make a speculative IAM matrix easier to express.
- Replacing the SPEC 02.1 permissions-boundary, human-role, source-user, backend, or exact PassRole architecture.
- Organization-level SCPs, SSO migration, customer-managed KMS keys, or broad Secrets Manager write permissions.
- Treating network isolation as a replacement for IAM restrictions.

## Data model

### Approval-time evidence contract

Before approval, classify each consumer as deployed, defined-but-disabled, or
future-only. Bind each deployed or defined-but-disabled function to:

| Field                                        | Required evidence                                               |
| -------------------------------------------- | --------------------------------------------------------------- |
| Terraform address and physical function name | Current Terraform configuration and plan                        |
| Unqualified function ARN                     | Validated account, Region, and exact physical name              |
| Execution-role ARN and permissions boundary  | Current IAM/Terraform configuration                             |
| Managed log-group ARN                        | Terraform-managed SPEC 06 resource                              |
| Secret ARN allowlist                         | Effective environment/configuration references                  |
| AWS actions                                  | Reachable SDK/API calls plus required Lambda service operations |
| Database destination                         | Exact RDS security group and PostgreSQL TCP `5432`              |
| Secrets destination                          | Exact endpoint security group and HTTPS TCP `443`               |
| Invocation principals                        | Terraform permissions and reviewed operator/deployment paths    |

Core migrations use their existing Terraform addresses and exact identities.
For the future-only Core API, record its proven source contract and missing
infrastructure fields with the future deployment spec as owner. Missing future
physical identifiers do not block A/B and must not be filled with invented ARNs.
No Core API resource, attachment, or endpoint principal is created here. Binding
those fields and testing them is mandatory before Core activation.

Use isolated fixture plans to test disabled Auth policies without enabling the
runtime in canonical state. Record local evidence separately from live evidence.

### Final permission matrix

| Principal category                 | Secret reads                                                                                       | Logs                                            | Administration                                                                                |
| ---------------------------------- | -------------------------------------------------------------------------------------------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Authentication execution role      | Application secret: `AWSCURRENT` and optional `AWSPREVIOUS`; runtime credential: `AWSCURRENT` only | Authentication log group streams only           | No master, migration, IAM, or administrative invocation privileges                            |
| Core execution role                | Existing `core_runtime` credential at `AWSCURRENT` only; no application signing secret             | Core log group streams only                     | No master, migration, IAM, or administrative invocation privileges                            |
| Authentication migration role      | Exact authentication migration credential only                                                     | Authentication migration log group streams only | Reviewed auth migrations only                                                                 |
| Core migration role                | Exact core migration credential only                                                               | Core migration log group streams only           | Reviewed core migrations only                                                                 |
| Administrative execution role      | Exact master and role credentials required by the currently enabled fixed bootstrap operation      | Administrative log group streams only           | Fixed private SQL bootstrap; no arbitrary AWS administration                                  |
| Reviewed human/deployment operator | Exact enablement and invocation permissions required by the runbook                                | Scoped diagnostic reads                         | Invoke only the exact administrative function and migration paths authorized by the procedure |

Auth uses `SECRET_ARN` and `DB_RUNTIME_SECRET_ARN`; Core uses
`CORE_RUNTIME_SECRET_ARN`. Both use `secretsmanager:GetSecretValue`.
`AWSPREVIOUS` is a version stage of the same Auth application secret ARN, not
another secret resource. An absent previous version is allowed by the loader;
an authorization failure must not be treated as an absent version.

Positive policy tests must allow Auth application-secret reads at both stages
and each runtime read at `AWSCURRENT`. Negative tests must reject cross-service,
master, operator, and migration secrets for API principals, and all secret-value
writes. If stage conditions are introduced, test their exact SDK request context;
do not restrict every read to `AWSCURRENT`. Keep the endpoint's principal/action/
resource permissions paired per consumer rather than granting every principal
the union of all secrets. Live stage checks for APIs belong to Phase C.

Core migrations already have exact resource names. Core API role, log group,
and security group identities will be bound by its future deployment spec;
its secret/username contract is established by SPEC 09 and SPEC 14.

Runtime and migration roles never write secret values. Credential initialization remains outside Terraform and normal application execution.

### Final IAM contract

- Use `logs:CreateLogStream` and `logs:PutLogEvents` only on the corresponding log group's stream ARN pattern.
- Remove account-wide `logs:CreateLogGroup` because Terraform owns all required groups.
- Retain only the EC2 actions Lambda needs to manage VPC interfaces.
- Apply the conditional `Deny` using each unqualified function ARN in `lambda:SourceFunctionArn` so function code cannot use those EC2 permissions while the Lambda service can.
- Keep any unavoidable `Resource = "*"` in its own documented statement with no unrelated action.
- Construct stable ARNs from validated account, Region, and physical names when a direct function reference would create a Terraform dependency cycle.
- Endpoint and identity policies must both authorize a Secrets Manager request.

### Bootstrap authorization and safe policy transition

The deployment role currently manages and attaches policies from exact ARN
allowlists. New stream/ENI policies cannot be installed merely by declaring them
in the application root. Inventory the existing bootstrap grants and explicitly
add only the required policy ARNs and role/policy attachment pairs before the
application transition. Include the necessary create/read/version/tag/detach
operations only where the actual Terraform lifecycle requires them. Do not
introduce wildcard IAM administration, new PassRole targets, or an unreviewed
principal. Preserve the SPEC 02.1 runtime boundary and human-role architecture.

Review/apply saved bootstrap capability plans before application plans. Install
and validate the replacement stream and VPC permissions before removing both
broad managed execution-policy attachments. The VPC managed policy also grants
logs permissions, so removing only the basic policy is insufficient. Verify
that Lambda resources' `depends_on` lists reference the new attachments.
Retain exact transition-only permissions until cleanup is verified, then remove
those no longer needed while retaining required steady-state management grants.
Document rollback by restoring reviewed policy attachments, never by destroying
functions, networking, secrets, state, or database data.

### Authorization evidence without false network denials

The private topology has no NAT or EC2/Logs API interface endpoints. An SDK
call timing out or failing DNS/TLS does not demonstrate an IAM denial.

For each defined function, evaluate its exact unqualified ARN as
`lambda:SourceFunctionArn` and require explicit denial of the selected
code-originated EC2 actions. With that key absent, prove this conditional Deny
does not match and the approved interface actions remain permitted by the
execution policy and boundary. Include aliases/versions using their underlying
unqualified function ARN. Separately verify required Lambda service interface
operations; invoking an already-attached function alone does not prove ENI
creation permissions.

Use IAM simulation when already authorized; otherwise use focused offline
condition/policy tests and clearly label their limits. Do not add permissions
or endpoints just to run a negative probe. Actual AccessDenied responses, when
available through an authorized reachable path, are separate live evidence.
Apply the same distinction to unused direct Logs API calls. Native Lambda log
delivery is a separate positive check and does not require a Logs endpoint.
For existing functions, verify the AWS-documented runtime permission set and
conditions; for absent APIs, hand future deployment checks to Phase C.

### Approved Admin evidence exception

This exception applies only to the existing `lambda_db_config` function. Its
only accepted operation is the stateful `bootstrap`: after validation it reads
the configured credentials, connects as the RDS master user, and reconciles
database roles/privileges in a transaction. Do not invoke it solely as an IAM,
secret, TLS, logging, or ENI probe. No behavior or event-contract change is
proposed.

For Admin, live policy/boundary inspection, focused offline policy tests, and
isolated IAM simulation are sufficient structural evidence to detach the two
broad execution policies. No bootstrap invocation is required or permitted as a
policy probe. The existing custom-policy simulation of the live replacement Logs
and VPC documents with boundary v7 returned allowed for the exact Admin log
group, implicit deny for another group, allowed for the AWS-documented VPC
actions then present (five; the set omitted `ec2:DescribeSubnets`) without
`lambda:SourceFunctionArn`, and explicit deny with the exact unqualified
function ARN. That historical simulation is not sufficient for the revised
six-action criterion; repeat it against the corrected documents before the
Admin detach plan. The evidence does not establish a live secret read,
PostgreSQL connection, or concrete native log write.

Admin's unexecuted runtime checks (secret retrieval, verified TLS/database
access, and native logging) are residual risk, not Phase B or closure blockers.
Verify them during the next necessary administrative execution and record the
result without invoking bootstrap solely for testing. This exception is Admin-
only and does not change its operation or event contract.

**Residual risk:** the custom-policy simulation is not a real Lambda service
request and does not settle concrete-stream matching, secret endpoint
reachability, TLS hostname/CA verification from Lambda, or actual log delivery.
Permission verification also cannot prove a real Lambda service ENI lifecycle.

### AWS-documented Lambda VPC permission evidence

For every existing function, verify the exact six Lambda execution-role actions
from the current [AWS Lambda VPC permissions documentation](https://docs.aws.amazon.com/lambda/latest/dg/configuration-vpc.html):
`ec2:CreateNetworkInterface`, `ec2:DescribeNetworkInterfaces`,
`ec2:DescribeSubnets`, `ec2:DeleteNetworkInterface`,
`ec2:AssignPrivateIpAddresses`, and `ec2:UnassignPrivateIpAddresses`.
Verify they are allowed on `*` under the configured `aws:RequestedRegion`
condition and that the code-originated conditional Deny matches each exact
unqualified function ARN but not when `lambda:SourceFunctionArn` is absent.
Verify the permission boundary retains the required allow ceiling. This
documented-permission check replaces observing a complete ENI lifecycle; it does
not claim that lifecycle was observed. AWS separately documents caller-side
permissions for changing a function's VPC configuration; those deployment
permissions are not required by this attachment-only transition and remain
outside this runtime-role check.

### Final network contract

- Each application, migration, and administrative Lambda has a separate client security group.
- Each client can initiate PostgreSQL TCP `5432` only to the RDS security group when its code requires database access.
- Each client can initiate HTTPS TCP `443` only to the Secrets Manager endpoint security group when its code requires secret retrieval.
- RDS ingress names every approved source security group and no broad CIDR.
- The endpoint security group names every approved source security group and no broad CIDR.
- Use standalone security-group rules where necessary to avoid mutual-reference cycles.
- The single-AZ Secrets Manager endpoint remains the accepted dev topology. Record its availability and cross-AZ cost tradeoff.

## Implementation plan

1. Classify the inventory by deployment state. Bind existing resources and
   disabled Auth configuration to actual identities; record Core's source-only
   contract and deployment-owned gaps. Reuse valid evidence from SPEC 09/14 and
   Core SPEC 06 without claiming live API verification.
2. Inventory effective policies/boundaries, SDK calls, version stages,
   invocation paths, logs, security groups, and exact secret references. Define
   replacement policy ARNs, attachment pairs, and focused positive/negative tests.
3. Prepare and verify exact bootstrap deployment capabilities. Review/apply the
   bootstrap saved plan before any application plan needs those permissions;
   preserve boundary/PassRole architecture and IAM quota guardrails.
4. Install scoped stream/ENI policies and per-function conditional denials.
   Update dependency edges and verify replacement policies before detaching
   broad basic and VPC execution policies. Test present/absent source-function
    context and verify all six AWS-documented Lambda VPC execution permissions
    for each existing function; no ENI lifecycle observation is required.
5. Reconcile paired secret allowlists and invocation grants. Test Auth signing
   reads at both required stages, runtime reads at AWSCURRENT, and denied
   cross-service/privileged reads and writes. Probes may resolve values only
   in authorized process memory; never print or persist them. Do not rerun the
   administrative bootstrap or rotate credentials merely to test a policy.
6. Apply exact client egress, RDS/endpoint ingress, and paired endpoint policy
   rules through reviewed saved plans. Preserve all currently enabled consumers
   and the reviewed private operator path; do not add future Core API principals.
7. Complete Phase B connectivity, TLS, native logging, and authorization checks
   for deployed resources except Admin's approved structural-evidence exception.
   Record Admin runtime checks as residual risk for its next necessary execution.
   Distinguish offline results, actual authorization errors, and network failures.
8. Document steady-state/transition permissions, revoke/re-enable and rollback
   procedures, cleanup grants, and final A/B evidence. Hand Auth's explicit
   pending live checklist to SPEC 10, Core's to its future deployment spec, and
   the resulting deployment contract to SPEC 11 without cross-API blocking.

## Decisions

- **Yes:** harden existing resources and prepare disabled Auth now; bind Core API infrastructure and run its live checks under its future deployment spec.
- **Yes:** keep SPEC 07 as a development baseline and SPEC 07.1 as a final deployment gate.
- **Yes:** include authentication, core, both migration executors, administration, and reviewed operator paths in one final matrix.
- **Yes:** retain narrow stream wildcards and unavoidable EC2 resource wildcards as documented exceptions.
- **Yes:** retain one Secrets Manager endpoint in one AZ for dev. Identity and endpoint policies both enforce access.
- **No:** invent absent Core API infrastructure identities or add an application signing secret that Core does not read.
- **No:** share an execution role or migration credential between authentication and core.
- **No:** require a blanket zero-wildcard policy claim.
- **No:** introduce NAT, a Logs endpoint, new KMS keys, or secret-write access to complete policy testing.

## AWS Free plan and cost constraints

This specification primarily replaces policies and security-group rules on existing resources. Policy checks must use features and permissions available to the actual account. If IAM simulation is unavailable, use the focused offline checks defined above and label them as offline evidence, not equivalent live authorization proof. Keep required Phase B service checks open until verified; do not add a paid analysis product.

No NAT gateway, additional interface endpoint, Paid plan upgrade, or persistent administrative environment is introduced. Record current endpoint cross-AZ traffic implications without changing the accepted single-AZ dev topology.

## Risks

| Risk                                                                      | Mitigation                                                                                                                              |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Future Core API resources block Auth or force speculative permissions     | Classify deployment states; require exact bindings at the owning deployment gate, without adding future principals here.                |
| A conditional denial blocks the service or a timeout masks missing denial | Test source-function context present/absent and distinguish authorization evidence from network failure and service lifecycle evidence. |
| Restricting logs interrupts diagnosis                                     | Create/import managed groups first and transition policies before removing managed attachments.                                         |
| Secret overrides fall outside the final allowlist                         | Derive the allowlist from effective validated configuration and test each approved override.                                            |
| Function ARN references create a Terraform cycle                          | Construct stable ARNs from validated identity and names when direct references would cycle.                                             |
| Mutual security-group references create a Terraform cycle                 | Use standalone directional rules and validate the Terraform graph.                                                                      |
| Endpoint policy blocks a legitimate client                                | Test the intersection of identity and endpoint policies for every exact principal and secret.                                           |
| A new application capability appears after hardening                      | Require a reviewed policy-matrix update before enabling the new capability.                                                             |
