# SPEC 02.2 — Secure Dev Foundation Deployment

> **Status:** Implemented
> **Depends on:** SPEC 01 (historical implementation reference), SPEC 02.1
> **Date:** 2026-10-15
> **Objective:** Authorize, deploy, and verify the private development network, protected RDS PostgreSQL instance, shared RDS CA layer, and exact bootstrap handoffs without deploying the authentication Lambda or public HTTP API.

## Why this spec exists

SPEC 01 created the application-root Terraform implementation, and SPEC 02.1
created the independent IAM, state, account, and secret-container control
plane. The next steps need a real private database and its generated master
secret ARN, but deploying the authentication Lambda now would temporarily give
application code the RDS master credential and expose controls that later
specifications are intended to harden.

This specification therefore replaces the foundation portion of the former
SPEC 14. It also absorbs the pre-first-apply RDS protection and deployment
readiness work from the former RDS-protection and infrastructure-risk drafts.
The final authentication Lambda and HTTP API deployment remains deferred to
SPEC 10.

## Scope

**In:**

- Reuse of the existing flat application Terraform root and canonical
  `gootip/dev/terraform.tfstate` backend from SPEC 02.1.
- Fresh project, account, Region, Free Plan, credit, quota, state, and caller
  verification before any potentially billable operation.
- A full application-root plan used only to inventory required AWS actions and
  detect unintended resources before deployment authorization is expanded.
- A separately reviewed bootstrap-root policy expansion for only the approved
  foundation actions.
- Deployment of the VPC, private subnets, required route tables, security
  groups, one private Secrets Manager interface endpoint, RDS subnet and
  parameter groups, the RDS PostgreSQL instance, and the shared RDS CA Lambda
  layer.
- A stable, explicitly selected single-AZ Secrets Manager endpoint topology for
  dev, with private DNS and no NAT Gateway or Logs interface endpoint.
- Explicit PostgreSQL engine and matching parameter-group-family selection
  verified through current RDS metadata before apply.
- `rds.force_ssl = 1`, the official Region-derived RDS CA bundle, deterministic
  layer packaging, and archive preservation from plan through apply.
- One-day automated backup retention under the active AWS Free Plan, deletion
  protection enabled by default, and a required stable operator-supplied final
  snapshot identifier. The recovery window is reduced from seven days to one.
- Private, encrypted, Single-AZ `db.t3.micro` RDS with
  `manage_master_user_password = true` and no Terraform-visible credential.
- RDS-first retrieval of only the generated master-secret ARN, followed by a
  separately reviewed bootstrap-root handoff that preserves the exact
  master-secret denial and runtime permission ceiling.
- Foundation-only state and live validation proving that no authentication
  Lambda, API Gateway resource, application execution role, secret value, or
  database schema mutation was deployed.
- Foundation deployment, rollback, teardown-protection, and failed-handoff
  runbooks.

**Out of scope (for future specs):**

- The `gootip-auth` Lambda, its execution role, Lambda permission, public HTTP
  API, route, stage, or CORS configuration; SPEC 10 owns their first deployment.
- PostgreSQL schemas, roles, ownership, grants, role-secret containers, or
  administrative invocation; SPEC 03 owns those resources and operations.
- Application migration execution; SPEC 04 owns the private migration path.
- Authentication runtime credential activation; SPEC 05 owns that contract.
- Final log, alarm, runtime IAM, endpoint-policy, traffic, concurrency, and
  credential-refresh controls owned by SPECS 06, 07, 09, and 11.
- Reading, creating, initializing, rotating, or managing any secret value or
  secret version through Terraform.
- Source-user cutover, CI/OIDC, staging, production, cross-account deployment,
  NAT, RDS Proxy, Multi-AZ, or a Paid plan upgrade.

## Data model and deployment gates

### Canonical foundation identity

| Item                | Contract                                                                      |
| ------------------- | ----------------------------------------------------------------------------- |
| Region              | `us-east-2`                                                                   |
| Application state   | `gootip/dev/terraform.tfstate`                                                |
| Deployment role     | `/gootip/deployment/GootipTerraformDeploy` through a fresh MFA-backed session |
| Database identifier | `gootip-dev`                                                                  |
| Database engine     | Explicit supported PostgreSQL version with matching family                    |
| Database class      | `db.t3.micro`, Single-AZ, private, encrypted                                  |
| Master credential   | RDS-managed; only its complete ARN may cross Terraform boundaries             |
| CA layer path       | `/opt/certs/rds-ca-bundle.pem`                                                |
| Runtime resources   | Absent until SPEC 10                                                          |

The foundation apply must use an explicit, reviewed resource set. A one-time
targeted bootstrap is acceptable only when its saved plan contains the exact
foundation dependency closure and no runtime or public resources. It is not a
general authorization for later targeted applies. A normal post-apply plan
must show only the intentionally deferred resources and must not propose a
foundation replacement.

### RDS protection contract

The normal dev configuration uses:

```hcl
backup_retention_period = 1
deletion_protection     = true
skip_final_snapshot     = false
multi_az               = false
```

The final snapshot identifier is a validated non-sensitive input with a stable
value for the database lifecycle. Authorized destruction requires a separate
reviewed operation that disables deletion protection, confirms an unused final
snapshot identifier, and reviews the resulting destroy plan. Cancelling the
teardown requires protection to be restored.

### Local operational records

Account IDs, generated backend files, complete generated secret ARNs, saved
plans, policy-action inventories, plan JSON, state snapshots, and live evidence
remain ignored local records. Tracked files contain only portable contracts and
non-sensitive values. No exception permits a secret value in Terraform, Git,
command arguments, plan output, or evidence files.

### Expected file changes

- Application root: `main.tf`, `network.tf`, `rds.tf`, `tls.tf`,
  `variables.tf`, `outputs.tf`, `environments/dev.tfvars`, and `README.md`.
- Bootstrap root: `bootstrap/iam.tf`, `bootstrap/variables.tf`,
  `bootstrap/environments/dev.tfvars`, tests, and `bootstrap/README.md` for the
  separately reviewed foundation and master-ARN policy handoffs.
- Repository conventions that still describe the superseded two-service,
  two-AZ endpoint topology must be updated to the accepted one-AZ Secrets
  Manager endpoint and native Lambda logging contract.
- No application source, Lambda function resource, API Gateway resource, or
  secret-value file is introduced by this specification.

## Implementation plan

1. Revalidate AWS Settings, caller identity, `us-east-2`, Free Plan eligibility,
   credits, expiration, quotas, canonical backend ownership, state emptiness,
   and a fresh `GootipTerraformDeploy` session. Stop on any mismatch, foreign
   state, unexplained lock, unknown denial, or unsupported service.
2. Complete pre-first-apply readiness in the application root: preserve
   Terraform 1.10+ and the reviewed provider lockfile, validate the explicit
   PostgreSQL version/family pair, require a stable final-snapshot input, set
   the protected RDS defaults, and ensure the foundation plan does not require
   the `gootip-auth` ZIP or a public application URL.
3. Reconcile the private network for the accepted dev topology: two private RDS
   subnets, no NAT, one explicitly placed Secrets Manager endpoint with private
   DNS, no Logs endpoint, and security groups that expose neither PostgreSQL nor
   the endpoint publicly. Leave final principal-specific endpoint policy and
   client egress tightening to SPEC 07.
4. Validate the official Region-derived CA response and deterministic archive,
   confirm that the layer contains only `certs/rds-ca-bundle.pem`, and document
   how the exact archive survives from the saved plan through apply.
5. Produce and save a full application plan without applying it. Record each
   required foundation action, resource scope, condition, wildcard reason,
   rollback, and expected denial. Prove that Lambda functions, application
   roles, API Gateway resources, secret versions, and database SQL are outside
   the approved apply set.
6. Apply only the separately approved bootstrap policy expansion. Mint a fresh
   deployment session and run positive and negative authorization checks before
   touching application state. Do not broaden PassRole or secret-value access
   for this foundation apply.
7. Apply the reviewed foundation plan. Verify the exact state additions, RDS
   protection, private networking, encryption, engine/family, TLS parameter,
   endpoint placement, CA layer hash and contents, and absence of public or
   runtime resources.
8. Capture only the complete RDS master-secret ARN and submit the reviewed
   bootstrap-root handoff. Preserve Terraform's value-blind contract, deny
   bootstrap access to the master value, and retain only the exact future
   runtime ceiling required by later approved specs.
9. Run refresh-free and normal post-apply plans with the same inputs. Confirm
   that foundation resources are stable and that all remaining changes are
   explicitly deferred. Record sanitized authorization, state, cost, and
   rollback evidence locally.

## Acceptance criteria

- [x] SPEC 01 remains the historical implementation reference and no second application root is created.
- [x] The canonical `us-east-2` account, backend, state key, bucket owner, and fresh deployment role are independently verified.
- [x] The reviewed foundation plan and its IAM expansion contain no unapproved application resource.
- [x] Terraform and provider versions are locked and the selected PostgreSQL engine version matches its parameter-group family.
- [x] The VPC, private subnets, route tables, foundation security groups, and one-AZ Secrets Manager endpoint are deployed without NAT or a Logs endpoint.
- [x] RDS is private, encrypted, Single-AZ, `db.t3.micro`, and uses an RDS-managed master password.
- [x] RDS has one-day automated backup retention under the AWS Free Plan,
  deletion protection, a required final snapshot, and a stable valid snapshot
  identifier. The reduced one-day recovery window is recorded.
- [x] `rds.force_ssl = 1` is associated with the database and no insecure server configuration is introduced.
- [x] The shared layer contains only `certs/rds-ca-bundle.pem`, uses the official `us-east-2` trust-store source, and is preserved unchanged from plan through apply.
- [x] Only the complete non-sensitive RDS master-secret ARN is handed to bootstrap; no principal or Terraform state reads its value.
- [x] No secret value/version, password, token, private key, or account-specific identifier is committed or added to Terraform state.
- [x] No `aws_lambda_function`, authentication execution role, API Gateway resource, public application route, or database schema object is created.
- [x] Refresh-free and normal post-apply plans show stable foundation resources and only reviewed deferred work.
- [x] The teardown runbook requires a separate protection-disable plan and a unique final snapshot before destruction.
- [x] Current eligibility, estimated foundation consumption, and cleanup obligations are recorded before the apply.

## Decisions

- **Yes:** deploy the private foundation before the application. PostgreSQL administration and live TLS verification need a real private database.
- **Yes:** stop before `gootip-auth` Lambda and API Gateway. The first application deployment must already use the restricted runtime credential and final IAM controls.
- **Yes:** absorb initial TLS, RDS protection, and deployment-readiness requirements here. Applying them after creating RDS would create avoidable insecure transitions.
- **Yes:** use one Secrets Manager endpoint in one selected AZ and no Logs endpoint for dev. Native Lambda logging does not require application VPC access to the Logs API.
- **Yes:** permit one explicitly reviewed foundation-only targeted apply when required by the existing flat root. It is an initial bootstrap exception, not the routine deployment model.
- **No:** deploy an authentication Lambda with the RDS master secret, even temporarily.
- **No:** use Terraform to create or transport secret values.
- **No:** activate source-user cutover or CI/CD as part of foundation deployment.
- **Yes:** keep the deployment Secrets Manager deny comprehensive while exempting
  only the account- and Region-scoped RDS-managed DB secret pattern from
  `CreateSecret` and `TagResource`. RDS creates that secret inside
  `CreateDBInstance`, and the exemption stays narrower than any other secret.
- **Yes:** scope deployment `rds:DescribeDBInstances` to the account/Region
  `db:*` ARN. The provider's post-create read evaluates the wildcard instance
  resource, and the role still cannot reach any instance outside this account.

## Risks

| Risk                                                                       | Mitigation                                                                                                 |
| -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| A targeted apply omits a required dependency or includes runtime resources | Save and inspect the exact dependency closure, then verify state and both post-apply plans.                |
| Engine and parameter family are incompatible                               | Resolve the supported version through current RDS metadata before approval and reject incidental upgrades. |
| Deletion protection blocks an authorized teardown                          | Use the documented separate disable-review-destroy sequence and restore protection if cancelled.           |
| A final snapshot name collides                                             | Validate syntax and inventory snapshots before authorizing destruction.                                    |
| The CA source changes between plan and apply                               | Preserve and hash the verified archive; do not redownload different bytes during apply.                    |
| A single endpoint AZ becomes unavailable                                   | Accept and document the dev availability tradeoff; do not claim Multi-AZ endpoint resilience.              |
| Foundation resources consume credits while later work is unfinished        | Verify current eligibility and cost, stop at the foundation gate, and retain an approved teardown path.    |
| Free Plan limits automated-backup retention to one day                     | Retain a nonzero one-day period, document the reduced recovery window, and do not upgrade the account plan. |

## What is **not** in this spec

- First deployment of `gootip-auth`, API Gateway, or any public route.
- PostgreSQL role bootstrap, application migrations, or runtime credential activation.
- Final observability, runtime IAM, endpoint-policy hardening, rate limiting, or warm credential refresh.
- Secret values, source-user cutover, CI/OIDC, staging, production, NAT, RDS Proxy, Multi-AZ, or a Paid plan upgrade.
