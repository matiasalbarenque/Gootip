## Why this spec exists

SPEC 10 completed initial Auth/Core deployment and basic security validation.
SPEC 08 tested the shared limiter, and SPEC 09 tested refresh and recovery in
isolated local environments. Repeating those matrices would add requests and
credential changes without resolving a new question.

This spec checks the remaining deployment-specific risks: behavior under modest
concurrent traffic, the deployed shared limiter, and the procedure and evidence
needed for credential transitions through Secrets Manager and verified RDS TLS.
Live transitions require an authorized PostgreSQL role-change procedure and remain
deferred until one is reviewed and authorized. This is a dev readiness check, not
a capacity benchmark or an exhaustive failure campaign.

## Required new exercises

### 1. One short operational traffic run

Use existing catalog data and one identified test identity. Obtain a session/JWT
only as needed to execute the scenarios. No user creation, repeated-login load,
full route/security sweep or standalone 60-second basic phase is required.

| Segment     | Maximum duration | Combined target rate | Maximum requests | Question answered                                                                                   |
| ----------- | ---------------- | -------------------- | ---------------- | --------------------------------------------------------------------------------------------------- |
| Normal use  | 60 seconds       | 5/second             | 300              | Do the deployed services remain healthy with modest concurrent traffic and bounded SQL connections? |
| Short burst | 5 seconds        | 20/second            | 100              | Does a brief spike produce controlled responses without connection growth or unexpected errors?     |

The 20 req/s burst is a target, not permission to exceed the concurrency bounds
below. If latency and the authorized in-flight limits prevent reaching it, record
the observed-rate result separately and defer the 20 req/s question as unproven.
Revisit only for a concrete capacity decision or changed latency, concurrency,
workload, or deployment conditions; do not repeat it merely to complete a target.

Send most traffic to Core catalog reads, with Auth session/JWT requests included
in normal use. Count setup/warm-up requests in the campaign. Record achieved
rates and successful-request latency per service; separate observed cold starts.
Do not force cold starts or claim capacity, cold-start coverage or a reliable
latency percentile from an insufficient sample. No minimum request count is a
pass requirement: assess whether the observations answer the segment's question.
If they do not, mark it pending and explain what evidence is missing.

Stop each segment on its duration or request limit. Cap requests in flight at
**5 per service, 10 combined**. No queued catch-up, duration extension or automatic
phase repeat. Keep the existing Gateway stage targets (10 requests/second, burst
20); never raise limits to make a test pass. Record observed Gateway/Lambda
throttling separately from the Auth limiter. An exact Gateway 429 count is not
required, and absence of a 429 does not prove throttling under overload.

### 2. One deployed shared-limiter check

Using an existing approved rule and fixed test identity/source/path, exercise
concurrent admission and rejection within its configured window. Record bounded
accepted/rejected counts and aggregate counter observations; do not create
arbitrary users, source identities or counter keys. Reuse SPEC 10's trusted-IP
checks and SPEC 08's local expiry, cleanup and storage-failure tests.

Claim live cross-Lambda-environment atomicity only if independent environments
are observed in the existing sanitized telemetry. Do not change concurrency or
add instrumentation/infrastructure solely to force that coverage. If not
observed, record deployed limiter behavior and retain multi-environment AWS
coverage as an explicit deferred limitation, supported by local independent-client
evidence. Unexpected over-admission or a bypass is a failure, never a limitation.

Read counter row counts before/after and observe existing cleanup opportunistically.
No dedicated expiry wait, cleanup stress test, forged-header matrix or live
storage outage is required with unchanged inputs and valid existing evidence.

### 3. Individual AWS credential transitions

Use a separately authorized window of at most **60 minutes and 500 application
requests**. These are ceilings, not targets. Do not run load, migrations or Admin
bootstrap concurrently. Retain refresh/retry/stale/drain settings of
**300/30/900/5 seconds**; do not shorten them for convenience.

The order is Auth database credential, Core database credential, then Auth signing
secret. The two database transitions passed on 2026-11-05 using the separately
reviewed temporary rotation authority. At the initial traffic closeout, none had
been executed. The existing `gootip_dev_operator` identity is `NOCREATEROLE` and has no
runtime-role administration membership under SPEC 05.1; the inspected private
operator access path therefore does not authorize either PostgreSQL password
change. Do not substitute the RDS master, invoke/redeploy `db_config`, expand IAM,
or change infrastructure to work around this gap.

Before any real rotation or rotation automation, review and explicitly authorize
a dev-only PostgreSQL role-change procedure/principal, including its least-
privilege scope, private secret handling, verified-TLS checks, matching-pair
recovery and stop conditions. The database campaign used that separately
reviewed procedure. The Auth signing transition uses the existing application
secret and is separate from PostgreSQL role changes. Local SPEC 09 tests and
Secrets Manager metadata observations alone do not establish AWS adoption.

When that prerequisite is approved, each database transition must verify the
changed version is adopted, the affected service works and retired generations/
connections are cleaned up before proceeding. Database verification requires a
fresh verified-TLS connection with the exact runtime identity; an old warm
connection is insufficient. Core must transition the whole Nest
application/DataSource/repository generation and close the retired application
with `app.close()`. Auth must transition its complete client/pool. Use existing
telemetry; do not rerun DDL, cross-schema or IAM negative matrices.
If later authorized, retain the implemented Better Auth versioned-key contract: publish
an increasing `BETTER_AUTH_SECRET_VERSION` and retain all required historical
keys in `BETTER_AUTH_PREVIOUS_SECRETS`. AWSPREVIOUS alone is not full key history.
Check supported retained-key data/JWT continuity and expected cookie
reauthentication using the identified test session. Do not claim uninterrupted
sessions or delete session rows as a shortcut.

After the PostgreSQL procedure is reviewed and authorized, prepare the secure
matching-pair/key recovery before starting. Do not inject an outage merely to
rehearse a path already covered locally. If a real transition fails, stop
subsequent changes and recover: restore a matching PostgreSQL/secret pair and
verify a new TLS connection, or publish a complete signing-key set with a new
higher version. Moving AWSCURRENT backward or code rollback alone is insufficient.
A deadline stops new scenarios, not required recovery; record any recovery
overrun. Never replay an ambiguous write/transaction.

### Agreed implementation direction — 2026-11-04

The user agreed to the following design for the pending rotations. This section
resolves implementation choices previously left open; it does not claim that a
rotation tool or rotation identity already exists. Design agreement does not
authorize live password changes, IAM grants or PostgreSQL role provisioning.
The reviewed exact permissions, secure procedure, recovery path and execution
window remain prerequisites to live execution.

- **Operator-run local tool:** implement a small helper under
  `gootip-infra/scripts/`, reusing existing access helpers where applicable. The
  human invokes it from a private workstation terminal after MFA authentication.
  This is a manually initiated, bounded maintenance operation, not scheduled
  rotation or CI/CD credential automation. Do not add a new Lambda or add a
  password-rotation operation to the administrative bootstrap in
  `gootip-db-config`.
- **Private PostgreSQL access:** reuse `scripts/db_access.sh` and its existing
  private tunnel host, endpoint discovery and reviewed CA material. Keep
  `verify-full` TLS and hostname verification. Adapt access only through a
  reviewed change if a separate rotation identity needs different credentials;
  do not silently repurpose the helper's fixed `gootip_dev_operator` identity.
  The tool runs locally, but password changes execute against the AWS dev RDS
  database. Close the tunnel and stop a host started by this operation afterward;
  preserve a host or tunnel already in use by another session.
- **Separate rotation authority:** retain `gootip_dev_operator`'s existing data
  access and do not broaden it to administer runtime roles. Use a separately
  authorized rotation identity/mechanism, provisionally named
  `gootip_credential_operator`, limited to changing `auth_runtime` and
  `core_runtime` passwords. Do not create a general-purpose
  `gootip_admin_operator`. The name alone grants nothing: design and review the
  exact PostgreSQL mechanism and associated AWS access before provisioning.
  Prefer temporary access; do not assume that granting `CREATEROLE` or role
  membership provides password-only authority. Keep PostgreSQL role permissions
  separate from the MFA-backed AWS profile's permissions.
- **Local Secrets Manager access:** the helper uses the AWS API over HTTPS with
  an explicitly selected, verified MFA-backed profile. This API path does not
  require the PostgreSQL tunnel or a new VPC endpoint. Allow only the reviewed
  reads and `PutSecretValue` writes on the exact existing target secret ARNs;
  do not assume the current database-operator profile already has those writes.
  No manual copy through the AWS console is required in the intended workflow.
- **Secret handling and coordinated writes:** obtain each new database password
  through hidden input in the operator's terminal and retain credential values
  only in process memory. Never pass passwords as command arguments or persist
  them in files, shell/SQL history, logs or chat. For each user, change PostgreSQL
  first, then immediately publish a new version of its matching existing secret
  with `PutSecretValue`. Preserve every unrelated payload field, including any
  Auth signing configuration. Verify the expected current version before writes,
  prohibit concurrent secret edits, and reconcile uncertain API outcomes rather
  than blindly retrying them. Do not introduce Terraform-managed secret values.
- **One user at a time:** complete Auth database rotation, fresh runtime-identity
  TLS verification, application adoption and retired-pool cleanup before starting
  Core. Complete the same checks for Core, including retired `app.close()`, before
  the separate Auth signing-key transition. The signing key is not a PostgreSQL
  password and must retain the existing increasing-version/key-history contract.
- **Recovery is part of the tool contract:** PostgreSQL and Secrets Manager do
  not share a transaction. A mismatch window can cause new connections to fail;
  do not promise uninterrupted service. Before changing either system, prepare
  a private recovery path with the authority needed to restore a matching pair,
  including after interruption of the local process. Review how recovery inputs
  remain securely available without plaintext files. On failure, stop later
  rotations, reconcile which writes committed and recover the current user
  before continuing. Do not rely on a code rollback or moving a staging label
  backward as sufficient recovery.

The read-only live check on 2026-11-04 confirmed `gootip_dev_operator` connected
with verified TLS, had data read/write access to Auth/Core application tables,
read-only migration histories, no `CREATEROLE` or superuser privileges and no
membership in the runtime/migration/admin roles. It changed no database data or
credentials and does not supply the missing rotation authorization.

## Campaign accounting and stop conditions

The reduced traffic run allows at most **400 requests**. A new traffic/security
campaign cap of **500 total application requests is proposed**, pending operator
confirmation: up to 100 additional requests cover setup, limiter probes, required
post-test session cleanup and retries. Before execution, allocate those requests
against the chosen rule/window; if the rule cannot be exercised within that cap,
review the allocation or budget before sending traffic. The earlier 1,000-request
proposal is superseded, not treated as approved. Neither cap is a spending target
or an API Gateway concurrency setting.

Record the confirmed cap, campaign ID, execution window, deployed bindings and
scenario allocation before live work. Enforce
`remaining = approved_campaign_cap - campaign_requests_used` across invocations;
count every application request, including failed attempts and retries. Preserve
the separate historical/recovery ledgers and the separate rotation ledger. Do
not reset counters or automatically start a new campaign after failure, expiry
or exhaustion. This Draft/documentation change does not authorize live traffic,
credential changes or optional infrastructure work.

Use read-only verified-TLS SQL sampling of aggregate client connections every
**2 seconds**, including the monitoring session. Supporting CloudWatch metrics
must not replace this short-test safety monitor. Stop new test work when:

- SQL monitoring is unavailable or any sample reaches **50 connections**.
- **3 consecutive unexpected HTTP 5xx responses** occur.
- After warm-up, per-service successful-request **p95 exceeds 2 seconds for
  30 seconds**, where the sample supports that measurement.
- Forbidden access, sensitive content or limiter bypass/over-admission is observed.

Expected 401/403/429 outcomes count as successful negatives only for the specific
probe that expects them. Do not hide ordinary failures as expected responses.
Stop traffic, let in-flight requests finish within their deadlines and preserve
sanitized evidence. Investigate before any reviewed retry. Any necessary
infrastructure recovery uses its own authorization and exact reviewed saved
plan; this spec does not authorize an apply or broader IAM/resource limits.

## Decisions and risks

- Reuse completed baseline checks and unchanged local correctness tests. Repeat
  only checks invalidated by changed inputs or needed to verify a new transition.
- Prefer one small observation that answers multiple operational questions. Do
  not add infrastructure, force failures or exhaust a budget for coverage alone.
- Combined rotations and several AWS failure paths
  remain unproven. Preserve that residual risk and require review and
  explicit authorization of a suitable PostgreSQL role-change procedure before
  any real rotation or automation.
- A small traffic sample cannot establish production capacity. Retain fixed
  request/concurrency/connection bounds and avoid extrapolating results.
- Required credential recovery outlives test deadlines. Preserve matching pairs,
  full signing-key history and secure operator handling throughout.
